    リージョンはAWSがサービスを提供している国や拠点を指す。
    リージョン同士は地理的に離れた位置に存在する。

    アベイラビリティゾーン(AZ)は複数のデータセンター(DC)から構成され、リージョンは複数のAZから構成される。

    リージョン > AZ > DC

    各AZ同士は地理的、電源的に独立した場所にあり、最低でも数十kmは離れているらしい。
    仮に災害等でAZの一つが使用不可になったとしても、リージョン内の他のAZでサービスを継続することができる。
    → 高耐久性、高信頼性の担保

    ただし当然ながらユーザー側が単一のAZにインスタンスを立てていた場合はオンプレとなんら変わりない。
    → 冗長的な マルチAZ で高耐久性を確保する。

    AZ 1にインスタンス 1、AZ 2にインスタンス 2を立てて、DBをメインからサブへレプリケーションする等すると、異なるサーバーへのアクセスも同じDBのデータを返すことができる。

    git remote add <リモート名> <リモートリポジトリのリンク> でorigin以外のリモートリポジトリを保持しておくことができる。
    → リンクには https か SSH のものを貼り付ける。

    2026/09/25 追記

    git clone 等したローカルリポジトリの中に生成される .git ディレクトリにより、リポジトリごとの情報が保持されているため、git branch や git remote といったコマンドはローカルリポジトリ配下でしか実行できない。
    さらに、一つのローカルリポジトリから複数のリモートリポジトリにpushするわけではないなら、git remote add で複数のリモートリポジトリを保持しておく理由は特になさそう。
    複数のリモートリポジトリをoriginとして設定するなら、
    git remote set-url --add <リモート名> <2つ目のリモートリポジトリのリンク>
    とすれば、git push とするだけで<リモート名>にsetされた全てのリポジトリのブランチにpushされる。

    個別のリポジトリにpushする時には、git remote add で追加したリモート名を指定する。

    git push <リモート名> <ブランチ名>

    余談だが、git push のように引数を省略した場合は、

    git config --global push.default

    で指定した設定でpushを行う。
    push.defaultの設定を変更したい場合は以下のコマンドで設定。

    git config --global push.default simple

    Virtual Private Cloud(VPC) とは、AWSの中核的サービス。
    AWSのほとんどのサービスを利用するためには前提として必要。

    一つのAWSアカウントに複数のVPCを立てることも可能だが、最近の構成は1アカウントに1VPCとして検証環境や開発環境、本番環境で別々のアカウント(VPC)を用意することで、他環境への影響をなくす手法が取られることが多い。

    VPCの中にはサブネット、そしてEC2やECS等が置かれるが、一昔前は単一VPCに環境別の複数のサブネット(EC2, ECS)を置いて、管理することも多かったらしい。
    → 単一VPCだとVPC自体に障害が起きた場合、全ての環境に影響が出てしまう可能性があるため、現在では望ましくない。

    CloudTrail のログもアカウントごとのため、環境別のログが判別しづらくなる問題もある。
    さらにアカウントごとに分ければ、環境別の料金も一目でわかる。

    → 1アカウントに1VPCがベストプラクティス

    VPCには、IPv4のCIDR(オプションでIPv6も可)を振り分ける必要がある。

    指定できないCIDRには以下の4種類がある。

    0.0.0.0/8
127.0.0.0/8 (内部ホストループバックアドレス範囲)
169.254.0.0/16 (リンクローカルアドレス範囲)
224.0.0.0/4 (マルチキャストアドレス範囲)
172.17.0.0/16(Cloud9とSageMakerの範囲)

    また、 RFC1918 によって定められているプライベートIPアドレスの割当の範囲外をVPC内のCIDRに指定しても良いが、同じIPアドレスで外への通信時にプライベート空間に接続されてしまうため、基本は RFC1918 の範囲内でCIDRを定める。

    10.0.0.0    -   10.255.255.255 (10.0.0.0/8)
172.16.0.0  -   172.31.255.255 (172.16.0.0/12)
192.168.0.0 -   192.168.255.255 (192.168.0.0/16)

    git reset <対象ファイル名.拡張子> でステージング(git add した状態)をリセットできる。
    → git reset . とすることで、全てのステージングをリセットできる。

    悪魔のコマンドと名高い rm -rf / だが、rm -rf <ディレクトリ名>/ のようにすれば確認をせずに強制的に指定ディレクトリ以下の全てのディレクトリ、ファイルを削除できる。

    ただしやはり危険(ヒューマンエラーはつきもの)なので、alias rm= としてrmコマンドの挙動を上書きしてしまうか、brew install trash-cli を実行してインストールしてから、 trash コマンドでゴミ箱に送ってしまうのが推奨されている。
    → 復元は trash-restore

    trash-cli は最近のmacOSには標準搭載らしい。


    論理削除について

    論理削除とは、DBでの削除データの扱いで delete_flg のような削除フラグで表にデータを出さないことで削除した様に見せかける手法。

    削除操作後もDBからデータを復旧したり、取得することができるため安心ではあるが、アンチパターンと呼ばれることもある。

    メリット デメリット
    心理的な安心感がある
    削除データを復旧させられる
    削除データを取得できる    		 データが肥大化することでパフォーマンス低下
    取得時の条件によるクエリ複雑化
    ユニーク制約の工夫が必要

    これを防ぐために、やはり一定期間で条件に引っ掛かるレコードはバックアップ(定期実行か削除時にログ出力等)を取った上で物理削除をする等で対策すると良いと思われる。
    → ユニーク制約に関してだけ言えば、別途 deleted_at カラムを作成し、email 等との複合ユニーク制約にすることで回避するという方法もある。

    論理削除が絶対に悪というわけではなく、ユースケースによる。
    → 例えばjoinが少ないとか、データ肥大化の恐れが少ないとか、ユニーク制約を考慮する必要がない等の場合は論理削除を採用しても良いと言える。
