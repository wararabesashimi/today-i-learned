    10-01

    ルートテーブルとはVPCごとに作成するトラフィックの通信路を決定する表。
    → 広義的にはルーティングテーブルとも呼ばれ、物理ハードでいうならルーターが保持している表である。

    最終的な送信先のIPアドレスや次のパケット送信先(AWS上ではtarget、インフラ的に言うならネクストホップ)などといった要素を持ち、送信先のIPアドレスが指定したCIDRに当てはまる場合、指定したネクストホップにトラフィックをルーティングする。


    物理ルーター ルーティングテーブルの例

    送信先 ネクストホップ ルーティング先
    8.8.8.8 ISP側のルーター インターネット
    192.168.0.10 directly connected 同一LANへ直接


    AWS VPCルートテーブルの例

    送信先 target ルーティング先
    8.8.8.8 igw-xxxx インターネット
    192.168.0.10 local 同一VPC内

    物理ルーターでは ルーター ∈ デフォルトゲートウェイ であり、ルーターから外へ出る通信の際にデフォルトゲートウェイという出口を通るというだけ。

    一方でVPCルートテーブルでは、VPCがルートテーブルを持っているため、targetは通信の出入り口となる IGW を選択する。

    10-02

    VPCのルートテーブルでは、送信先(CIDR、または プレフィックスリスト )のIPアドレスに基づいてtargetを IGWや NAT GW 等の様々なネクストホップに転送することができる。

    プレフィックスリストとは、CIDRブロックの集まり。

    例えば、192.168.0.0/24, 10.0.0.0/24をプレフィックスリストAに設定しておき、プレフィックスリストAのtargetを local にすると、上記2つのCIDRへの通信に対しては同一VPC内の宛先を探すというルーティングになる。

    ルートテーブルはVPCごとに作成できるが、関連付けられるのは サブネット か GW の2つ。
    → 1:Nの関連付けが可能だが、1つのサブネットに2つ以上のルートテーブルを関連付けることはできない。

    サブネットに明示的なルートテーブルが関連付けられていない場合は、VPC作成時に自動的に作られたメインルートテーブルが関連付けられる。

    アウトバウンド通信においては、サブネットにルートテーブルを関連付けてtarget先にトラフィックをルーティングする。

    インバウンド通信においては、EC2インスタンス一つ一つに対応付けされたパブリックIPアドレスがIGWによって管理され(1:1 NAT)、ルートテーブルがなくてもインスタンスを一意に特定することができる。
    → あるいは ロードバランサー(LB) にパブリックIPアドレスが割り当てられているので、そのままインバウンド通信がやってきたら一意に特定できる。

    あくまでこれはルーティング(道案内)の話であり、アクセス制御をするのは ネットワークACL や セキュリティグループ 等による設定が別途必要。

    10-03

    ( xdg-utils パッケージがインストール済みの)Linuxなら、xdg-open コマンドで指定したファイルをアプリケーションで開くことができる。

    xdg-open ファイルパスorURL

    このようにすることで、そのファイルに関連付けられているデフォルトのアプリでファイルを開くことができる。
    → URLにした場合、デフォルトのブラウザでURLを開く

    とはいえGUIベースでもないのにブラウザを開くことはないだろうが…

    ちなみにUnixでは open コマンドになる。

    2026/10/13 追記

    Unix(MacOS)では、パスはわかってるけどVSCode上だとどこにファイルがあるかわからない…
    といった時にアプリ名まで指定しなくても open パス/ファイル名 とすると大体VSCodeで開いてくれるので意外と重宝している。

    ちなみに明示的にアプリ名を指定したい場合は　open -a "アプリケーション名" ファイルパス とすると指定したアプリで開ける。
    → アプリケーション名は /Applications か ~/Applications 配下の拡張子を除いたファイル名を指定する。

    10-06

    セキュリティグループ(SG) と ネットワークACL(NACL) はどちらもVPCの通信制御を行う。

    その中でもSGはインスタンス単位での通信制御を行う仮想ファイアウォールであり、SG1つに対してN個のインスタンスをアタッチできる。

    デフォルトではアウトバウンドは全許可、インバウンドは全拒否となる。

    なおインスタンスには必ず1つ以上のSGが必要で、デフォルトでは1つのインスタンス(NIC)に5個までアタッチできる
    → クォータ引き上げを申請すれば、最大16個までアタッチ可

    SGごとの最大ルール数はNICごとにインバウンド/アウトバウンドともに60個ずつだが、クォータ引き上げを申請すると最大1000個までルールを設けられる。
    → ただし、1000 ≧ <SGのルール数> * <NICにアタッチされたSG数> に収まらなければならない。

    セキュリティグループはステートフルなため、戻りの通信に対しての別途ルールを設定する必要はない。

    プロトコル 、ポート範囲 、送受信先のCIDR か SG の3つを制御項目として設定する必要があり、指定しない場合は ALL と指定する。

    例：0.0.0.0/0:TCP:22
→ 全てのIPアドレスからのTCPプロトコル：22番ポートを使用した通信を許可

    SGを指定した場合は、指定したSGがアタッチされたインスタンスからの通信のみ許可する。
    → SGに自分自身を設定することで、オートスケーリングの際に増減するインスタンスが動的に相互通信を行えるようになる。

    CIDRとSGを追加すると、そのSGがアタッチされたインスタンスと指定されたCIDRからの通信(CIDR側はSGのアタッチを必要としない)という、OR条件にすることもできる。

    最後に、SGにおいてAmazon DNSやDHCP、サブネットごとの予約アドレス(先頭4つと最後1つ)等はフィルタリング対象とならない。

    10-13

    コンテナ技術とは、アプリケーションや依存関係をまとめて一つにしてパッケージ化した実行環境を作る仮想化技術。

    VM(仮想マシン)と比べてゲストOSを持たず、起動も非常に高速でデータ容量も少ない。

    コンテナ VM
    OS ゲストOSを持たない ゲストOSを持つ
    起動速度 数秒 数分
    容量 MB単位 GB単位

    2026年10月現在、コンテナは各社OSベンダーから提供されており、主に

    • Linuxコンテナ
    • Windowsコンテナー
    • Apple Container

    の3種類がある。（他にあるかはわからない）

    Linuzコンテナは従来のコンテナ技術を用いた仮想環境であり、ホストOSをの持つLinuxカーネルを共有し、その上でプロセスごとに別環境(コンテナ)を立てる
    → Linuxカーネルが必要であるため、WindowsでもMacでもLinuxが必要である(WindowsならWSL2、MacならDocker等のプラットフォームが必要)

    ちなみにMacOSはLinuxカーネルを持たないため、実際にはLinuxKit等を用いて軽量な仮想Linux VMを立てて動作している。

    コンテナを実現するプラットフォームには様々あるが、代表的なのは Docker だろう。


    仮想化ソフトウェア

    1台の物理的なマシンの上で、複数のOSを動かすためのソフトウェア。
    主な仮想化ソフトの種類には、3種類ある

    • ホスト型
    • ベアメタル型
    • コンテナ型

    この内、ホスト型とベアメタル型はVMを作成し、実行・管理する。
    ex）VMWare, VirtualBox, Hyper-V, KVM 等

    コンテナ型は、OSからカーネル部分のみを共有してコンテナを作成、実行・管理する。

    10-16

    DockerはLinuxコンテナ型の仮想化ソフトウェア。

    • Docker Engine
    • Docker CLI
    • Docker Desktop

    etc...

    といった様々なコンポーネントが存在する。

    PCにLinuxカーネルが含まれていれば、DockerはLinuxカーネルを共有してその上にLinuxコンテナを立てる。
    → 一つのLinuxの上に独立したプロセスがコンテナとして動いている。

    MacだとそもそもLinuxカーネルが存在しないため、Linux VMを立ててその上でLinuxコンテナを動かす必要があり、暗黙的にLinux VMを立てる Docker Desktop の利用が必至となる。
    → 特定の条件下においては有償となるため、注意が必要。

    Windows11においては、 WSL というWindows上でLinuxを動かせる仕組みを利用できるので、Docker DesktopがなくてもWSL上のLinuxにDocer CLIを導入すれば動作するらしいが、少々設定が必要。
    → WindowsでもDocker Desktopを利用するほうが個人利用としては楽。

    Docker DesktopはLinux VMを立てるだけでなくGUIでコンテナ管理ができる点もメリットはある。

    実際にDocker上でコンテナを立てる時には、 Docker Image という設計図からコンテナを作る。
    → Docker Image は公式イメージをそのまま使うか、 Dockerfile をビルドしてDocker Imageを作る。

    Docker Imageが準備できたら、 docker run コマンドでコンテナを起動できる。

    開発においては Docker Compose というツールで、複数のコンテナをまとめて起動することが多い。
    → Docker ComposeはYAMLファイルで設定を記述する。

    起動中のコンテナは、

    - docker stop
- docker start
- docker restart
- docker compose down
- docker conpose up

    等のコマンドで起動・終了・再起動等ができる。
